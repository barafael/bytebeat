# Existing Rust DAW / tracker / sequencer / live-coding projects (plus collaborative music tools): status, stacks, and architecture lessons (as of 2026-09-26)

> Method note: Most non-GitHub websites (codeberg.org, lib.rs, docs.rs, billydm.github.io, wikipedia, news sites) were blocked by this environment's egress proxy. Facts below therefore come mainly from (a) shallow `git clone`s of the GitHub repos (READMEs, design docs, Cargo.toml, source comments, last-commit dates), (b) the crates.io API (versions/dates/downloads), (c) GitHub search (star counts, captured 2026-09-26), and (d) web-search result snippets where no primary page could be fetched (flagged as "search snippet"). Billy Messenger's blog posts were read from the blog's source repo (github.com/BillyDM/billydm.github.io, `content/blog/*.md`); I cite the public blog URLs. Star counts are approximate and as of 2026-09-26. "Last commit" = last commit on the default branch of the GitHub repo.

## 1. Meadowlark (MeadowlarkDAW): status in 2026, why it was paused/restructured, spin-off crates (Firewheel, creek, dropseed, rusty-daw-*, pcm-loader/Symphonium) and their usability

### Takeaway
Meadowlark still has no usable release: it was put on hiatus in April 2023 after its author burned out and found the GUI much harder than expected. In September 2025 its GitHub repos were turned into "moved to Codeberg" stubs, and the old code now sits only on `old`/`dev-(old)` branches. The pieces that survived are small, reusable, game-oriented crates: **Firewheel** (audio-graph engine, v0.14.0, Sept 2026, being upstreamed into Bevy), **Symphonium** (the renamed pcm-loader, used for file loading) and **creek** (disk streaming). The DAW-engine crates (dropseed, rusty-daw-core, meadowlark-core-types) have been dormant since 2022. Firewheel is maintained, WASM-capable, and has sample-accurate scheduled events and an optional musical transport. Its own design doc says it is **not** a DAW engine.

### Cited Findings

The license badge now says AGPLv3; the old branch's Cargo.toml says GPL-3.0. — [Meadowlark README](https://github.com/MeadowlarkDAW/Meadowlark); [old Cargo.toml](https://raw.githubusercontent.com/MeadowlarkDAW/Meadowlark/old/Cargo.toml)
- The last GitHub commit is 2025-09-21 ("adjust centering in readme"). Stars ≈1.5k (1,497), 51 forks. — [GitHub repo](https://github.com/MeadowlarkDAW/Meadowlark)
- The GitHub branches show several abandoned GUI attempts: `gtk4-(old)`, `vizia`, `yarrow-(old)`, `prototype-(old)`, `dev-(older)`, `dev-(old)`, `old`. — [Meadowlark branches](https://github.com/MeadowlarkDAW/Meadowlark/branches)
- The old-branch README said: "Meadowlark and all its subprojects are in a temporary hiatus while I restructure things and figure out a plan on how to move forward with this project." — [old README](https://github.com/MeadowlarkDAW/Meadowlark/blob/old/README.md)
- Stack of the old prototype: vizia GUI, cpal 0.14, rtrb 0.2, basedrop 0.1, pcm-loader, and in-repo `meadowlark-engine`/`plugin-api` crates. — [old Cargo.toml](https://raw.githubusercontent.com/MeadowlarkDAW/Meadowlark/old/Cargo.toml)
- Old design doc: the engine (dropseed) was meant to provide "a highly flexible audio graph system with automatic delay compensation and summation of edges, as well as … plugin hosting (with a special focus on CLAP plugins)", using the `audio-graph` crate for "pure abstract graph compilation" and `clack` for CLAP bindings. Non-MVP plans included running the engine plus plugin hosting in an isolated process for crash protection. — [Meadowlark DESIGN_DOC (old)](https://github.com/MeadowlarkDAW/Meadowlark/blob/old/DESIGN_DOC.md)
- **The design doc explicitly doubted real-time online collaboration**: "Creating custom networking protocols that are reliable is *hard* … fine if the state you are syncing is fairly simple like a text document or an SVG file, but the state of a DAW application is much more complicated." And: "A DAW doesn't have complete control over how the state of 3rd party plugins is defined. We would have no choice but to send over the entire save state of a 3rd party plugin … and even then there is no guarantee that the plugin on the other user's end will load that state properly." The fallback it proposed was a shared "collaboration panel" that works like a shared network drive for clips, presets and tracks. — [Meadowlark DESIGN_DOC (old)](https://github.com/MeadowlarkDAW/Meadowlark/blob/old/DESIGN_DOC.md)

**Why it was paused (post-mortems by Billy Messenger)**
- 2023-02-21, "DAW Frontend Development Struggles": "I've really underestimated how difficult it would be to develop the frontend/GUI". He lists DAW-specific GUI problems: constant redraws for meters; expensive clip rendering (waveform peak search, automation curves, MIDI minimaps); zoomable timelines that make caching hard; huge file browsers that need virtualized lists; pointer-lock for knobs; global shortcuts even while a plugin window has focus; raw window handles for hosting plugin GUIs. — [blog](https://billydm.github.io/blog/daw-frontend-development-struggles/)
- The same post describes **three states that must be kept in sync**: the save-file "source state", the GUI state and the backend (realtime) state. They are needed because units differ (beats in the source, samples in the backend, pixels in the GUI). The realtime thread "cannot just use simple mutexes" and needs lock-free channels or GC'd copy-on-write pointers (basedrop `SharedCell`). Uncommitted GUI state (e.g. dragging a clip) should only be committed on mouse-up, "otherwise it would cause expensive updates to happen every single frame". Missing plugins need placeholders that don't overwrite saved state. — [blog](https://billydm.github.io/blog/daw-frontend-development-struggles/)
- 2023-04-14, "Why I'm Taking a Break from Meadowlark": he cites being overwhelmed, the social job of managing a large project, and scope: "Even the MVP features alone are turning out to be quite difficult". Someone suggested "creating something simpler like a tracker before creating a full-blown DAW". — [blog](https://billydm.github.io/blog/why-im-taking-a-break-from-meadowlark/)
- Same post, on architecture: "My original plan … was to just wing it … The code began to get really messy and hard to follow with a lot of interconnected parts", and a real technical design document was needed. — [blog](https://billydm.github.io/blog/why-im-taking-a-break-from-meadowlark/)
- Same post, on repo sprawl: he split code into many crates and forks (dropseed, rainout, creek, pcm-loader, meadowlark-plugins, audio-waveform-mipmap, audio-graph, clack fork, samplerate forks …) and found "managing so many repositories is a headache". — [blog](https://billydm.github.io/blog/why-im-taking-a-break-from-meadowlark/)
- Same post, on Rust vs C++: "A part of me kind of regrets choosing Rust … If I used C++, I could have just used JUCE", and porting C++ plugin DSP to Rust is "yet another time sink". He still says "Rust is the future. Especially when you have a team". — [blog](https://billydm.github.io/blog/why-im-taking-a-break-from-meadowlark/)
- Same post, on GUI switching cost: "switching GUI libraries after the fact isn't trivial, especially if you have a lot of custom widgets". Bitwig and Ableton built in-house GUI toolkits. — [blog](https://billydm.github.io/blog/why-im-taking-a-break-from-meadowlark/)
- 2023-05-16, "Clarifying Some Things": "You can't rely on volunteers to build key components of a large open source project". "I simply cannot make both a DAW engine and a DAW frontend on my own." He planned Dropseed as a Tracktion-Engine-like modular Rust DAW engine with first-class CLAP, paired with a third party's Flutter frontend. — [blog](https://billydm.github.io/blog/clarifying-some-things/)
- 2024-04-05, "2024 Update": he dropped the Flutter collaboration ("I truly stay motivated best on large projects when working alone") and decided to write his own GUI library (later **Yarrow**) plus a GPU vector renderer (**RootVG**). — [blog](https://billydm.github.io/blog/2024-update/); [RootVG post](https://billydm.github.io/blog/rootvg/)
- Yarrow's last crates.io release is 0.0.1 (2024-06-06) and RootVG's is 0.1.0 (2024-04-05), with no releases since. The blog's last post is 2024-12-01 (Vitalium reverb update). — [crates.io yarrow](https://crates.io/crates/yarrow); [crates.io rootvg](https://crates.io/crates/rootvg); [blog source repo](https://github.com/BillyDM/billydm.github.io)
- 2022-11-21, "Accurate Timekeeping in a DAW": use musical time as the **source of truth** for notes, automation and clip starts, and sample/"superclock" time for audio-clip internals. Convert only *from* the source of truth, never back. Store time as **fixed point**: musical ticks = 1/1,476,034,560 beat (LCM of common subdivisions, above all sample rates, fits in u32), and superclock = 1/282,240,000 s (divisible by all common sample rates; the same value Ardour uses). On any tempo-map change, convert every event to samples and send the result to the audio thread. — [blog](https://billydm.github.io/blog/time-keeping/)

**Spin-off crates, status**
- **Firewheel**: v0.14.0 released 2026-09-05; ≈52k total downloads; ≈310 stars; ~692 commits since Jan 2025, active every month (e.g. 85 in 2026-03, 11 in 2026-09). — [crates.io firewheel](https://crates.io/crates/firewheel); [GitHub](https://github.com/BillyDM/Firewheel)
- Firewheel README: "An open source audio graph engine for games and other applications … can be used as-is, or … as a base for other higher-level audio engines". It is "currently planned to be upstreamed into the Bevy game engine where it will become the default audio engine", partly "to ease the maintenance burden of a project that has experienced more feature creep than … anticipated". The core stays usable outside Bevy, depending only on `bevy_platform`. — [Firewheel README](https://github.com/BillyDM/Firewheel)
- Firewheel features: any DAG with fan-in and fan-out, cycle detection, built-in nodes (volume, pan, peak meter, sampler with sequencing and Doppler, filters, convolution, delay compensation, stream reader/writer), custom-node API, an ECS-friendly data-driven parameter API, per-buffer **silence flags** (`ProcInfo::in_silence_mask`) to skip work, "no mutexes", `no_std` support, and stream fault tolerance (unplugging headphones must not crash the app). — [README](https://github.com/BillyDM/Firewheel); [DESIGN_DOC](https://github.com/BillyDM/Firewheel/blob/main/DESIGN_DOC.md)
- Firewheel architecture: the context compiles the graph into a "schedule" sent to the realtime processor over a realtime-safe message channel. The app calls `update()` about once per frame to flush grouped events. There are three clocks (seconds, samples, musical), and events can be delayed sample-accurately. Cargo features: `scheduled_events`, `musical_transport`, `cpal` (default), `rtaudio` (better full-duplex latency, desktop only), `symphonium`, `node_profiling`. Crates: firewheel-core, -graph, -nodes, -cpal, -rtaudio, -symphonium, -macros. — [DESIGN_DOC](https://github.com/BillyDM/Firewheel/blob/main/DESIGN_DOC.md); [Cargo.toml](https://github.com/BillyDM/Firewheel/blob/main/Cargo.toml)
- **Why Firewheel is explicitly not a DAW engine**: "the needs of game audio engine and DAW audio engine are in conflict … In a DAW, the state is tied to the state of the 'transport', and the host is allowed to discard any user-generated parameter update events that conflict with this transport state … in a game engine … parameter update events are only allowed to come from a single source (the user), and are guaranteed to not be discarded." Other non-goals: MIDI and parameter events at graph level (partly worked around via `ProcStore`), multithreaded graph processing, VST/VST3/LV2/AU hosting, hosted plugin GUIs. CLAP hosting is only a future goal. — [DESIGN_DOC](https://github.com/BillyDM/Firewheel/blob/main/DESIGN_DOC.md)
- **Firewheel's WASM rules**: no C or system-library dependencies (so no CLAP hosting on WASM), no file I/O ("Asset loading is out of scope"), don't spawn threads ("the audio backend … should be in charge of spawning the audio thread"), don't block threads. creek is disabled on WASM. — [DESIGN_DOC](https://github.com/BillyDM/Firewheel/blob/main/DESIGN_DOC.md)
- Firewheel's default web path goes through `firewheel-cpal`'s `wasm-bindgen` feature (cpal's WebAudio host). A separate crate, **firewheel-web-audio** (in the bevy_seedling repo, v0.5.0, 2026-08-09), is "a multi-threaded `wasm32-unknown-unknown` Web Audio backend" that runs the graph inside an `AudioWorkletNode`. It is stereo-only and needs nightly Rust with `build-std`, `+atomics`, shared memory, and COOP/COEP headers. Its changelog says 0.5.0 targets Firewheel 0.12, so it lags the core by two minor versions. — [firewheel-web-audio README](https://github.com/CorvusPrudens/bevy_seedling/tree/master/crates/firewheel-web-audio); [crates.io](https://crates.io/crates/firewheel-web-audio)
- **bevy_seedling** (Firewheel's Bevy integration): v0.8.0 (2026-08-09), ≈157 stars. Its features include `web_audio` ("multi-threading web backend"), `rtaudio`, `hrtf` and `loudness`. — [bevy_seedling](https://github.com/CorvusPrudens/bevy_seedling); [crates.io](https://crates.io/crates/bevy_seedling)
- **creek** (realtime-safe disk streaming via Symphonia): a separate "IO server" thread, cache buffers (e.g. for loop starts) and a look-ahead buffer. WAV-only encoder. v1.2.3 (2025-09-22), ≈120k downloads, ≈138 stars. The repo moved to Codeberg; the GitHub copy is a stub. — [creek README](https://github.com/MeadowlarkDAW/creek); [crates.io](https://crates.io/crates/creek)
- **pcm-loader → Symphonium**: "An unofficial easy-to-use wrapper around Symphonia for loading audio files. It also handles resampling at load-time", and it keeps native sample formats to save memory. v0.13.0 (2026-08-28), ≈59k downloads. It lives on Codeberg; the GitHub repo is archived. — [GitHub stub](https://github.com/MeadowlarkDAW/pcm-loader); [crates.io symphonium](https://crates.io/crates/symphonium)
- **dropseed** ("An open source DAW engine for Meadowlark"): crates.io holds only a 0.0.0 placeholder (2022-06-14); the GitHub stub says "moved to Codeberg". **rusty-daw-core**: 0.9.0 (2022-04-24), dormant. **meadowlark-core-types** (the fixed-point time types): 0.3.0 (2022-07-15), dormant. — [dropseed](https://github.com/MeadowlarkDAW/dropseed); [crates.io dropseed](https://crates.io/crates/dropseed); [crates.io rusty-daw-core](https://crates.io/crates/rusty-daw-core); [crates.io meadowlark-core-types](https://crates.io/crates/meadowlark-core-types)
- **NIH-plug** (Robbert van der Helm's plugin framework) is "currently in maintenance mode", and the README points to a community fork at codeberg.org/BillyDM/nih-plug. Last GitHub commit 2026-09-03; ≈3k stars. — [nih-plug README](https://github.com/robbert-vdh/nih-plug)

### Inferences
- Meadowlark's GitHub footprint looks like a project reset: the stubs point to Codeberg, and the old code is on `(old)` branches. Without Codeberg access I can't say whether new DAW code exists there. What has shipped since 2023 is Firewheel, Symphonium and creek, not a DAW.
- For a *miniature collaborative* DAW, Firewheel is the most relevant spin-off. It gives a WASM-capable DAG engine with sample-accurate scheduling and a musical clock. But its "user is the single source of truth, events are never discarded" model means a DAW-style transport and sequencer would sit **on top** of it, in the app. That fits a small DAW whose sequencer feeds scheduled events into a Firewheel graph.
- Lessons to copy: (1) keep the source (document) state, GUI state and realtime state separate, and commit only on gesture end; (2) use fixed-point musical time as the source of truth; (3) avoid repo and crate sprawl in a small team; (4) pick the GUI early and keep scope small (a tracker or groovebox before a full timeline DAW); (5) define plugin-state handling before attempting real-time collaboration.

### Gaps
- Current contents and activity of codeberg.org/Meadowlark/* (Meadowlark, Dropseed, creek, Symphonium) could not be checked (Codeberg blocked). Whether Meadowlark has new code in 2025-2026 is unknown.
- I found no official statement on when Firewheel will actually land in a Bevy release. Only the README's "planned to be upstreamed" is confirmed.
- No benchmark or latency numbers for Firewheel on the web were found.

## 2. Other Rust music apps (DAWs, trackers, sequencers, grooveboxes, live coding): catalog with status, stack and architecture

### Takeaway
As of September 2026 no Rust DAW is production-ready, but more hobby and early-stage DAWs are active than ever: generic-daw (iced), Maolan (CLAP/VST3/LV2 host; its own `maolan-widgets`/`maolan-engine` crates; GUI toolkit not verified), Futureboard Studio (GPUI native plus React/WASM web, with a collaboration server), yadaw (egui, web preview), vibez, Volt, chipbox and ShoopDaLoop (live looper, native plus browser). Almost all use **cpal + rtrb + symphonia** for I/O, lock-free messaging and decoding, and the GUI toolkit is where they diverge. Tracker-style Rust apps are rare and small; the best-known sequencers are Chiptrack (Slint, runs on the web and GBA), Cacophony and Typebeat (both stale). Glicol is the flagship Rust live-coding engine but has had few commits since early 2025.

### Cited Findings
**DAWs (desktop-first)**
- **generic-daw**: "early-in-development, open source, cross-platform DAW built in Rust". ≈155 stars. Very active: last commit 2026-09-23, about 1,650 commits since Jan 2025. Stack: iced GUI, cpal 0.18.2 (ASIO + PipeWire features), rtrb, crossbeam, symphonia, midir, clack-host (CLAP hosting). Workspace crates: `audio_graph`, `thread_pool`, `clap_host`, `dsp`, `generic_daw_core`, `generic_daw_gui`, `generic_daw_project`, `generic_daw_widget`. The project file format uses **protobuf (prost)** plus compression. Binaries are built by CI. — [generic-daw](https://github.com/generic-daw/generic-daw)
- **Maolan**: "a Rust DAW focused on recording, editing, routing, automation, export, and plugin hosting". Unix builds host CLAP, VST3 and LV2; Windows hosts CLAP and VST3. ≈146 stars. Last commit 2026-09-26; development burst of about 570 commits in Feb–Mar 2026. Dependencies include `maolan-engine`, `maolan-widgets`, ratatui, crossterm, tokio, rubato, timestretch and arc-swap. — [Maolan](https://github.com/maolan/maolan)
- **Futureboard Studio** (created 2026-05; ≈87 stars; last commit 2026-09-25): "native Rust application built on GPUI (the rendering framework behind the Zed editor), driving an in-process Rust audio engine". A secondary web surface ("Futureboard Lite", React + TS + Vite) runs a separate WASM DSP core (`SphereWebAudioCore`, "transport, flat audio graph (tracks → master), mixer, and meters … run in an AudioWorklet"). There is also a collaboration server ("stream sync and file hosting for collaboration"). — [Futureboard README](https://github.com/futureboard/futureboard-studio); [ARCHITECTURE.md](https://github.com/futureboard/futureboard-studio/blob/main/ARCHITECTURE.md)
- Futureboard's architecture doc says **"The two engines are intentionally separate. Do not try to unify DAUx and the web core into one runtime; they target different constraints (professional low-latency native I/O vs. a sandboxed AudioWorklet). Shared concepts live in descriptors and IDs … not in shared realtime code."** The web surface "lags [native] in feature coverage and does not host native plugins." — [ARCHITECTURE.md](https://github.com/futureboard/futureboard-studio/blob/main/ARCHITECTURE.md)
- **yadaw**: "An sfx creation tool and midi player that doesn't crash often (web (preview) can boot and play audio)". egui/eframe, cpal, rtrb, symphonia, VST3/LV2 hosting, Android support. It notes "No Web runtime plugin support … since libloading cant be used on wasm". Created 2025-07; ≈71 stars; last commit 2026-09-26. On Flathub and AUR. — [yadaw](https://github.com/mlm-games/yadaw)
- **vibez** ("An open-source DAW for electronic music, written in pure Rust"; created 2026-02; ≈32 stars; v0.3.3 on 2026-09-26): iced, cpal, rtrb, audio_thread_priority, VST3, symphonia. — [vibez](https://github.com/alexanderwanyoike/vibez)
- **Volt** ("a custom DAW"; ≈70 stars; last commit 2026-06-19): GPUI, cpal 0.18, creek, symphonia. — [Volt](https://github.com/TheRedXD/Volt)
- **chipbox** ("Open-source DAW with a node graph system"; ≈138 stars; last commit 2026-01-09): a QuickJS runtime (rquickjs) running a SolidJS/TypeScript frontend inside the app, rendered through a custom DOM-based DSL with wgpu. Planned: node-graph audio, CLAP/VST, and extensibility via WASM, Lua or JS. — [chipbox](https://github.com/chipnertkj/chipbox)
- **ShoopDaLoop** (live looper "with DAW elements"; ≈59 stars; last commit 2026-09-09): runs natively (CPAL + midir, or a dedicated JACK driver, with Carla plugin hosting) **and in the browser** through a "repository-owned Web Audio/AudioWorklet backend" plus Web MIDI. Browser recording is capped at 120 s per channel, with memory reserved when a loop is armed "so dormant loop slots do not exhaust Wasm memory". — [ShoopDaLoop](https://github.com/SanderVocke/shoopdaloop); [technical README](https://github.com/SanderVocke/shoopdaloop/blob/master/src/rust/shoopdaloop/README.md)

**Live coding**
- **Glicol** ("Graph-oriented live coding language and music/audio DSP library written in Rust"; ≈3k stars). Crates: `glicol_synth` (engine), `glicol_parser` (pest), `glicol_macros`, `glicol_ext`, and `glicol_wasm`. The engine started on `dasp_graph`, and v0.4 added an "LCS algorithm and preprocessor for smooth and efficient whole graph updating" (the graph is diffed on re-evaluation rather than rebuilt). — [Glicol README](https://github.com/chaosprint/glicol)

- The author "decide[d] to do it the hard way", writing parser and engine in Rust rather than mapping onto SuperCollider, and ported it "to browsers using WebAssembly, AudioWorklet and SharedArrayBuffer … to explore performant audio in browsers for easy access and live coding collaboration". ### Inferences
- The de-facto Rust DAW plumbing is cpal (I/O), rtrb or crossbeam (lock-free GUI↔audio messages), symphonia/Symphonium (decoding), rubato (resampling), midir (MIDI) and clack (CLAP). The GUI is the axis of disagreement: iced, egui, GPUI, Slint, vizia, ratatui, or a web stack via Tauri or QuickJS.

- generic-daw's use of protobuf for the project file and Audiotool's protobuf entity schema (Q4) both point to a typed, schema-versioned document model as a sensible base for sync.
- Many of the most-starred sequencer and live-coding projects (Typebeat, Cacophony, and Glicol to a degree) went quiet after 1–3 years. Single-maintainer burnout is the main risk, as the Meadowlark post-mortem also shows.

## 3. Rust audio apps running in the browser via WASM (cpal web backends, AudioWorklet, web-audio-api-rs): what they learned (AudioWorklet, SharedArrayBuffer, COOP/COEP, latency)

### Takeaway
There are two workable browser patterns. (a) **Single-threaded WASM instantiated inside the AudioWorklet**, controlled by `postMessage`. This works on stable Rust, needs no special headers, and is what Glicol's current JS does. (b) **Multithreaded WASM with shared memory**, where the worklet shares linear memory with the main/UI thread (cpal's `audioworklet` host, firewheel-web-audio, waw-rs). This needs nightly Rust + `build-std` + `+atomics` plus COOP/COEP cross-origin isolation, and Safari has caveats. cpal's *default* web host still uses the deprecated main-thread `ScriptProcessorNode`, so it is not what you want for a DAW. web-audio-api-rs is the opposite direction: the Web Audio API reimplemented in Rust for native use, with Node bindings.

### Cited Findings
- **cpal hosts**: `webaudio` is the "Default backend on WebAssembly" and is built on `ScriptProcessorNode` (source imports ScriptProcessorNode; the buffer size must be a power of two within the spec range). The separate `audioworklet` host gives "lower-latency web audio than the default Web Audio API, running audio on a dedicated thread". It "Requires atomics support (`RUSTFLAGS="-C target-feature=+atomics,+bulk-memory,+mutable-globals"`) and `Cross-Origin` headers for `SharedArrayBuffer`" and needs `-Zbuild-std`, so nightly. — [cpal README](https://github.com/RustAudio/cpal/blob/master/README.md); [webaudio host source](https://github.com/RustAudio/cpal/blob/master/src/host/webaudio/mod.rs); [audioworklet host source](https://github.com/RustAudio/cpal/blob/master/src/host/audioworklet/mod.rs)
- The cpal AudioWorklet example's Trunk config sets `cross-origin-embedder-policy: require-corp`, `cross-origin-opener-policy: same-origin`, `cross-origin-resource-policy: same-site`. Its README: "requires a nightly version of Rust to enable WebAssembly atomics and to recompile the standard library". — [cpal audioworklet example](https://github.com/RustAudio/cpal/tree/master/examples/audioworklet)
- The cpal changelog shows the web hosts are still being fixed in 2026: 0.18.x fixes "dropouts in output streams when the callback buffer grows", "stale audio output when a data callback wrote a partial buffer", and an unsound `Send + Sync` with `+atomics`. `BufferSize::Fixed` sets `renderSizeHint`. WebAudio timestamps now include base and output latency. The Emscripten host was removed. Unreleased: AudioWorklet/WebAudio input and duplex streams. — [cpal CHANGELOG](https://github.com/RustAudio/cpal/blob/master/CHANGELOG.md)
- **firewheel-web-audio** (Firewheel's AudioWorklet backend): needs nightly + `rust-src`, `+atomics`, linker args (`--shared-memory`, `--import-memory`, `--max-memory=1073741824`, TLS exports), a secure context (https), and `Cross-Origin-Opener-Policy: same-origin` with `Cross-Origin-Embedder-Policy: require-corp` (or `credentialless`). It warns that "`credentialless` may not work on Safari: the browser may throw an error in the audio worklet upon receiving shared Wasm memory." Stereo only. — [firewheel-web-audio README/lib.rs](https://github.com/CorvusPrudens/bevy_seedling/tree/master/crates/firewheel-web-audio)
- **Glicol web**: the main thread fetches `glicol_wasm_bg.wasm` as bytes and passes them via `processorOptions` to an `AudioWorkletNode`. The processor calls `initSync(wasmBlob)` inside the worklet, and control is by `port.postMessage` (`run` = new code string, `bpm`, `amp`, `loadsample` = Float32Array sample data). The `"sab"` (SharedArrayBuffer) message branch is commented out in current code, although the README roadmap (v0.5.0) says SAB was adopted. Glicol's JS also embeds a customised copy of Paul Adenot's ringbuf.js. — [glicol.js](https://github.com/chaosprint/glicol/blob/main/js/src/glicol.js); [glicol-engine.js](https://github.com/chaosprint/glicol/blob/main/js/src/glicol-engine.js); [README roadmap](https://github.com/chaosprint/glicol)
- Glicol's stated benefit of Rust + WASM in an AudioWorklet: "near-native, garbage-collection-free and memory-safe real-time audio" with zero installation. — [Glicol README](https://github.com/chaosprint/glicol)
- **ShoopDaLoop web**: the audio engine runs in a dedicated AudioWorklet WASM module, while a single `raw_wasm_host.js` owns "module instantiation, ABI buffers, command/response bytes, process calls, memory-view recovery, and destruction". The worklet "retains track-route truth" and a bounded main-thread hub handles Web MIDI. Audio starts only after an explicit user enable action (autoplay rules). The engine "runs at the context's actual sample rate and render quantum". The browser may override requests to disable echo cancellation, noise suppression and AGC. HTTPS or localhost is required. — [ShoopDaLoop technical README](https://github.com/SanderVocke/shoopdaloop/blob/master/src/rust/shoopdaloop/README.md)
- **Futureboard Lite** runs a flat track→master graph WASM core in an AudioWorklet, separate from the native engine (see Q2). — [ARCHITECTURE.md](https://github.com/futureboard/futureboard-studio/blob/main/ARCHITECTURE.md)
- **waw-rs** ("Rust Web Audio Worklets without crying"; ≈18 stars): uses `web-thread` and SharedArrayBuffer multithreading and needs `+atomics,+bulk-memory`. Self-described as "all very experimental". — [waw-rs](https://github.com/Marcel-G/waw-rs)
- **web-audio-api-rs**: "A pure Rust implementation of the Web Audio API, for use in non-browser contexts". v1.7.0 (2026-08-08), ≈386 stars. Node.js bindings at ircam-ismm/node-web-audio-api (≈263 stars). It can pipe output back into a browser through cpal's wasm-bindgen backend, but that path is marked "Warning: experimental!". — [web-audio-api-rs README](https://github.com/orottier/web-audio-api-rs); [crates.io](https://crates.io/crates/web-audio-api); [node-web-audio-api](https://github.com/ircam-ismm/node-web-audio-api)
- Blog tutorials on Rust→WASM Web Audio exist, such as Casey Primozic's FM synth with WASM SIMD and his wavetable synth (known from search results only; not fetched). — [cprimozic FM synth](https://cprimozic.net/blog/fm-synth-rust-wasm-simd/); [cprimozic wavetable](https://cprimozic.net/blog/buliding-a-wavetable-synthesizer-with-rust-wasm-and-webaudio/)
- **libymfm.wasm** (Yamaha FM cores as WASM in AudioWorklet/WebWorker; ≈66 stars) is another example of the worklet approach. — [libymfm.wasm](https://github.com/h1romas4/libymfm.wasm)

### Inferences
- For a mini DAW that must run in the browser, the least risky path is a stable-Rust, single-threaded engine instantiated **inside** the AudioWorklet. Commands go over `port.postMessage` or a SAB ring buffer. The engine owns its own graph (Firewheel's `no_std`-friendly core, fundsp, or a custom graph) and does not rely on cpal's default web host. Use the multithreaded shared-memory path only if you need the UI to share memory with the engine, and accept nightly Rust plus COOP/COEP, which also restricts embedding third-party iframes and cross-origin assets.
- Browser worklets render in fixed 128-frame quanta (cpal notes the spec-required minimum render quantum). Design the engine's block size to accept whatever the host gives rather than assuming a fixed buffer.
- Keep file I/O, decoding and network sync off the audio thread on both targets. Firewheel's WASM rules (no file I/O, no thread spawning, no blocking in the engine) are a good checklist.
- One Rust engine can serve both native (cpal/rtaudio) and web (AudioWorklet), as Firewheel and Glicol do. Futureboard's experience argues against forcing *pro-level* native features (plugin hosting, low-latency duplex I/O) into the same runtime as the web core.

### Gaps
- No measured latency numbers (ScriptProcessor vs. AudioWorklet vs. native) were found in these repos.
- I could not fetch Glicol's papers or blog to confirm why the SAB path was dropped in favour of postMessage. That it was dropped is inferred from commented-out code only.
- Not verified: whether Bevy's official web audio will use firewheel-web-audio or cpal once Firewheel is upstreamed.

## 4. Collaborative music tools (any language) to learn from: Flok/Strudel (Yjs), Audiotool, Glicol, Endlesss, others (concise)

### Takeaway
Collaborative live-coding tools (Flok, Glicol) sync **text** with the Yjs CRDT and broadcast "evaluate" events separately, so each client runs the audio locally. Audiotool, the most advanced collaborative browser DAW (v3.0 "multiplayer" relaunch in 2026, NEXUS SDK), uses a **server-authoritative, protobuf-typed entity document**. Clients apply optimistic local transactions, the server can reject them, and a consolidator reconciles the two, with undo/redo kept client-side. Neither model streams audio between users: they sync the *project or code* and render locally.

### Cited Findings
- **Flok** ("Web-based P2P collaborative editor for live coding music and graphics"; ≈374 stars; GPL-3): the GitHub repo is archived and development moved to codeberg.org/munshkr/flok (last GitHub commit 2025-06-18). It integrates Strudel (`@strudel/*` 1.2.x), Hydra, Tidal and Punctual. — [flok README](https://github.com/munshkr/flok); [GitHub search result](https://github.com/munshkr/flok)
- Flok's sync layer: a `Y.Doc` with one `Y.Text` per editor pane, and presence via `y-protocols` `Awareness`. Three providers are used together by default, `["webrtc", "websocket", "indexeddb"]` (y-webrtc P2P, y-websocket server relay, and y-indexeddb offline persistence), with optional extra signaling servers. The server middleware hosts a y-websocket endpoint. — [flok session.ts](https://github.com/munshkr/flok/blob/main/packages/session/lib/session.ts); [server-middleware](https://github.com/munshkr/flok/tree/main/packages/server-middleware)
- Flok's **evaluation** is not part of the CRDT. `session.evaluate()` either emits locally ("web"/"webLocal" modes) or publishes to an `:eval` topic on a separate WebSocket **pub/sub** service ("used for remote code execution and message passing in Flok"), which auto-reconnects and uses ping/pong. Each browser renders Strudel audio itself. — [session.ts](https://github.com/munshkr/flok/blob/main/packages/session/lib/session.ts); [pubsub README](https://github.com/munshkr/flok/tree/main/packages/pubsub)
- **Strudel**: the GitHub repo was archived on 2025-06-19 ("MOVED TO CODEBERG"), with development continuing at codeberg.org/uzu/strudel. ≈3k stars. Several live-coding projects moved to Codeberg "for ethical reasons" (search snippet). — [strudel GitHub](https://github.com/tidalcycles/strudel); [MOVED_TO_CODEBERG.md](https://github.com/tidalcycles/strudel/blob/main/MOVED_TO_CODEBERG.md); [HN thread](https://news.ycombinator.com/item?id=44317358)
- **Glicol** lists "Decentralised collaboration using `yjs` and a unique `be-ready` mechanism" (the mechanism is not described in the README). — [Glicol README](https://github.com/chaosprint/glicol)
- **Audiotool** (browser DAW): search snippets say the 2026 relaunch ("Audiotool 3.0"/"Audiotool Studio") was "rebuilt from scratch to support real-time multiplayer music creation across web browsers and tablets" and that "the 2026 version was built on Rust" (attributed to Wikipedia in search results; not verified from a primary source). NEXUS launched as an open beta in January 2026. — [Mixdown (snippet)](https://mixdownmag.com.au/news/audiotool-3-0-launches-with-multiplayer-daw-and-open-sdk/); [TechPlugged (snippet)](https://techplugged.com/audiotool-3-0-rebuilds-the-browser-daw-as-a-multiplayer-sandbox-with-its-own-sdk/); [Wikipedia (snippet)](https://en.wikipedia.org/wiki/Audiotool); [Gearnews (snippet)](https://www.gearnews.com/audiotool-studio-nexus-daw-tech/)
- **Audiotool NEXUS SDK** (`@audiotool/nexus`, TypeScript, v0.0.19 on 2026-09-26, "Expect breaking changes … pre 1.0"): "A JS package allowing you to programmatically control the Audiotool DAW." Per search snippets, NEXUS is "built on Protocol Buffers, and defines every entity and action in the DAW: from devices and cables to effects, automation … and is the same API the app uses internally". — [nexus README](https://github.com/audiotool/nexus); [developer docs (snippet)](https://developer.audiotool.com/js-package-documentation/)
- NEXUS sync internals (from source): `NexusDocument` "contains mechanisms to sync that data with other clients and the backend in a conflict-free manner" and manages "undo/redo history" (changes grouped by `actionId`). Edits happen inside a **transaction lock** ("While a transaction builder exists, no other can be created"). The `CollabGateway` sends each local transaction (given a random UUID) over a retrying gRPC/Connect `DocumentService`. The server may **reject** transactions, and `synchronize()` calls a WASM "consolidator" with the received, rejected and sent transactions to produce the resulting state. Every modification is validated locally first by a validator described as "Validates all modification using the go wasm", so the shared document logic is compiled to WASM from **Go**, not Rust, in the SDK. — [document.ts](https://github.com/audiotool/nexus/blob/main/src/document/document.ts); [gateway.ts](https://github.com/audiotool/nexus/blob/main/src/document/backend/document-service/gateway.ts); [wasm-nexus-validator.ts](https://github.com/audiotool/nexus/blob/main/src/document/backend/document-service/wasm-nexus-validator.ts)
- **Endlesss** (Tim Exile's loop-jamming "Rifff" app, launched 2020): servers closed on 31 May 2024 when Endlesss Ltd ceased operations, and users were told to download their music. — [MusicTech](https://musictech.com/news/gear/tim-exile-endlesss-app-shut-down/); [Music Ally](https://musically.com/2024/05/24/music-creation-startup-endlesss-is-shutting-down-this-month/); [CDM](https://cdm.link/endlesss-discontinued/)
- **Ableton Link from Rust**: `rusty_link` (bindings via the official `abl_link` C wrapper) 0.4.9 (2026-04-02), ≈37 stars. The older `ableton-link` crate (2019) is stale. — [rusty_link](https://github.com/anzbert/rusty_link); [crates.io](https://crates.io/crates/rusty_link)
- Rust CRDT options in active development (for context): `yrs` (Yjs port) 0.28.0 (2026-09-17, ≈3.5M downloads), `loro` 1.16.2 (2026-09-21), `automerge` 0.12.0 (2026-09-16). — crates.io: [yrs](https://crates.io/crates/yrs), [loro](https://crates.io/crates/loro), [automerge](https://crates.io/crates/automerge)
- Academic precedent: "Multi Web Audio Sequencer: Collaborative Music Making" (arXiv 1905.06717). Surfaced by search only; not read. — [arXiv](https://arxiv.org/pdf/1905.06717)

### Inferences
- For code or pattern collaboration, Flok's split is a clean reusable pattern: a CRDT for document text, a separate low-latency pub/sub for "events" (evaluate, transport start), and local audio rendering on each client. Timing alignment across clients is not solved by Yjs itself.
- For structured DAW state, Audiotool shows a server-authoritative, schema-typed (protobuf) entity-component document with optimistic transactions, server rejection and rebase. Undo is kept per client, and validation logic is shared between client and server via WASM. A Rust implementation could compile the same validation crate to native, server and WASM. A CRDT (yrs, loro, automerge) is the peer-to-peer alternative, but it needs app-level invariants (e.g. no cycles in routing, valid parameter ranges) enforced after merge.
- Both approaches avoid Meadowlark's feared problem (opaque third-party plugin state) by syncing only first-party, schema-defined devices. This supports keeping plugins out of a collaborative mini DAW.
- Endlesss's shutdown shows that server-dependent collaborative music tools risk user lock-in when the company folds. Local-first persistence (as in Flok's IndexedDB provider) and exportable project files reduce that risk.

### Gaps
- Could not verify from a primary source that Audiotool 3.0's engine is written in Rust. The only primary code seen (the NEXUS SDK) uses a Go-compiled WASM validator/consolidator, and the Rust claim comes only from search snippets. Treat it as unconfirmed.
- Glicol's "be-ready" mechanism is undocumented in the sources I could access. Flok's handling of clock sync across peers was not found.
- BandLab/Soundtrap sync internals, Jamulus/JackTrip, Sonic Pi, Hydra and Estuary were not researched in depth (time and tool budget, and many sites were blocked). General knowledge suggests Jamulus/JackTrip stream audio at low latency rather than sharing project state, but this is not cited here.

## 5. State of Rust audio for app-building in 2025–2026 (community, blogs, "are we audio yet", GUI)

### Takeaway
The low-level Rust audio stack is healthy and actively maintained in 2026: cpal 0.18/0.19 is gaining duplex and web input, Firewheel is headed into Bevy, and clack, Symphonium/Symphonia, fundsp, kira and rtrb all released in 2026. ### Inferences
- For a *miniature* collaborative DAW, Rust's gaps matter less than for Meadowlark. A small, fixed feature set with first-party devices only (no plugin hosting) avoids the plugin-framework and plugin-GUI problems.
